## Performance

| Condition | CPU (% of one core) | Private memory |
| --- | --- | --- |
| USB, Xbox 360 emulation, window open, idle 30 s | 0.94% | 114 MB |
| Bluetooth (730 reports/s), Xbox 360 emulation, window open, idle 60 s | 2.5–4.0% total: 0.6% user, 2.9% kernel | 128–140 MB |

Targets: CPU ≤ 2% of one core, private memory ≤ 150 MB.

- Memory meets the target on both transports.
- CPU meets the target over USB. Over Bluetooth the app's own work (user mode) is 0.6%; the rest is kernel time in
  the Windows Bluetooth HID stack. The controller sends 730 reports per second and every HID read returns one
  report. A `dotnet-trace` sample puts the read thread's time inside the HID read call, while parsing, the ViGEm
  submit (0.13%) and the UI are negligible. Reading less often would only add input lag, so the Bluetooth total is
  accepted above target.
- Fixes made during acceptance: the controller drawing redraws only on visible input changes (resting stick noise
  had redrawn it at the display rate), and the virtual pad is only resubmitted when sticks, triggers or buttons
  change.
